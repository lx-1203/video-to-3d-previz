# 原声、4K与最终交付

## 规格表必须来自当前任务

下面是来源项目的**范例合同**，不替代新任务的用户规格：

| 项目 | 来源项目约定 |
|---|---|
| 每片核心文件 | 可编辑Blender工程、带原声白模MP4、上原片下白模MP4 |
| 白模画幅 | 原生3840×2160，不能把低清渲染放大冒充原生4K |
| 上下对照 | 3840×4320，每格3840×2160；不拉伸、不擅自裁切 |
| 帧率 | 用户表最低24fps；该项目原片30fps，输出保持30fps及全部帧 |
| 视频 | MP4 / H.264，实测视频码率至少18Mbps，建议30Mbps |
| 音频 | AAC立体声，至少44.1kHz，实测至少320kbps；项目用48kHz |
| 音频中间格式 | 16bit或32bit PCM，不使用24bit；项目采用16bit WAV |

来源参数图还要求参考视频4K，但实际给到的是1280×720。应记录输入不足：放大参考栏只满足输出尺寸，不能凭此宣称原片质量达标。更高分辨率原片需要用户提供或明确接受现有输入限制，不伪造源信息。

“上下对照4K”需区分整张画布4K和每格4K。该项目采用后者；新任务尺寸不明确时先解释这一区别，避免擅自把两格压成1920×1080。两份影片应使用同一白模帧序列与同一时间映射。

AAC不是PCM位深格式。不要用播放器显示的 float sample format 来宣称压缩音轨“32bit无损”。分别记录PCM中间文件位深、AAC编码、采样率、声道和实测码率。

## 原声保留链

1. 从对应原片直接提取音轨，保存不重编码的原压缩音频副本；无法流复制的容器情况明确说明。
2. 按统一解码参数创建时间轴WAV，保留原起点、尾部及全部内容，不擅自去噪、归一化、配音、加噪、改速或叠加原片与白模的两条声音。
3. 将WAV内嵌Blender，另提供正确相对路径的外部资产副本。另存后重开检查 packed 数据、路径、VSE起点、音量及是否静音。
4. 对最终两种视频只编码一次音轨，两次封装复制同一份AAC；比较AAC包序列可证明两片共用声音。
5. 与原片按同参数解码的PCM比较声道、样本、波形相关性、采样级延迟及尾段；与原压缩音轨比较时区分流复制与有损转码。

重新编码后的AAC不能宣称与原AAC字节一致。内容/时序一致、两份输出AAC一致、原AAC归档一致是三个不同结论。相关系数很高也不单独证明无丢尾、无错声道或听觉完全相同；应结合采样与实际试听。

封装前检查视频和音频分别的起止时间。不要无条件使用 `-shortest` 或以视频时长截掉真实原声音尾；也不要为凑容器时长加静音或改变内容。按原片的音画尾部关系处理并记录。

## 码率不能只看命令

来源项目中，默认AAC即使请求512kbps，部分实际素材也只有约264kbps，未达到320kbps。曾使用本机FFmpeg的 `-aac_coder fast -aac_ms 0 -aac_is 0 -aac_pns 0 -b:a 384k`，实测约384kbps。这是当时版本与素材的可行配置，不保证所有编码器都支持或所有素材都达标。

先检查当前编码器帮助及短段真实素材的结果，再整片编码。不能通过加噪、叠音、改声道内容或伪造标签提高音频码率。若支持的配置仍无法兼顾原声与目标参数，准确报告约束冲突。

视频可按要求选择真实CBR配置；来源项目用H.264 high、level6.0、yuv420p、30Mbps和HRD/filler。尺寸/帧率不同需重新核对级别与播放器支持，不照抄level；填充数据可满足传输码率但不提升细节质量。

实测按各流编码包总字节×8/该流时长计算，并记录时长定义、编码包与元数据值；不能用总文件大小除视频时长代替独立视频/音频码率。验证可用FFprobe或PyAV等本机工具，记录实际工具版本。

## 渲染来源与磁盘

原生渲染先出带连续帧号的序列，清单记录实际尺寸、帧段、相机、引擎/设置、输入SHA和每帧SHA。同一目录不混入旧候选。缺帧、重复帧、坏帧都阻止编码。

估算剩余磁盘：用几帧实际PNG均值×剩余帧数，加两份编码暂存、审核图和必要余量；估算随渲染更新。无损PNG压缩可降低空间，不能用降低分辨率替代。

批量渲染前，用当前引擎与实际原生4K代表帧比较几个PNG压缩设置的写出耗时和文件体积，再按磁盘、吞吐和并行资源选取。压缩数值高不自动等于总成本更低，低清试验也不能可靠估算4K写出成本；记录实测环境与样本，保留PNG的原生尺寸和无损属性，不把某次最优参数写成通用默认。

只在已核对有效工程、成片、资产和重建条件后清理可再生缓存。Windows使用同一PowerShell上下文：解析绝对路径，确认位于批准的缓存目录内，仅删除明确模式的帧文件，保存清理清单。不得把源视频、原工程、音频、唯一审查证据或整个production目录当缓存删除；不因磁盘紧张清理其他任务。

用户授权清理过渡版本时，还可逐项处理已被取代的试渲、重复编码包和可重建候选工程。先查当前入口、构建脚本的读取依赖和版本回退需要，保留不可替代输入、客户模板、当前有效工程/资产/成片、必要修前基线及能说明失败的最小证据。删除清单记录绝对路径、类型、字节数、保留替代物与重建依据；旧`.blend`若仍被补丁链读取就不是可删缓存。Windows递归操作前核对解析目标确在本任务范围，识别junction/链接的真实落点；不要以整个历史目录代替逐项判断，也不要把删除后失效的旧链接继续当当前交付入口。

## 成片验证与当前入口

- 完整解码最终MP4的视频和音频，检查尺寸、fps分数、准确帧数、逐帧时间戳、总时长、编码、像素格式、声道及实测码率。
- 在每镜、每个关键事件、切点两侧，从最终MP4按既定时间抽帧，与冻结渲染序列对比；上下片分别核对上栏原片、下栏白模。
- 加查本次修改区域，防止大面积未变化背景掩盖蓝色角色仍是旧动作。PSNR等可用于检查“成片来自哪版渲染”，不能当真人对白模的创作相似度。
- 可行时正常速度播放并听取音轨，确认运动连贯、无突闪和声音同步。工具启动失败就记未验证，联系表与全解码不是已完成实时回看。
- 只有本次交付范围的发布条件成立、报告SHA相符，才更新总清单和当前版本入口；中间候选、旧版和已被用户否决的版本保留清楚标识。用户授权的部分交稿入口须标为“交稿版/未结反馈”，不能覆盖或冒称“全部验收通过”的状态与历史记录。
- 包报告除了复算自身引用路径的SHA，还要与实际选中的工程、渲染帧清单及最终媒体逐项匹配：选中工程SHA应对应清单的源SHA，帧段/数量/尺寸/相机对应本次渲染，媒体及其抽帧对应所选帧序列，当前入口指向这些文件。旧版报告连同旧文件可以完全自洽，仍不代表当前交付正确；选择依据应来自当前批准记录或交付清单，不能由待验证报告自行指定。
- 如果视觉范围仍有残差但允许交付修订，标签写“修订文件/已接受增量/未通过整体目标”，不把技术发布等同全部验收通过。

只有明确的非视觉修复（如内嵌声音外部相对路径）才考虑复用旧帧：保留原渲染源SHA，对受影响整段的求值几何、变换、显隐、相机、灯光、材质、渲染设置及相关依赖验证画面不变，另取实际渲染样本验证，并记录父子版本桥接。证明不足就重渲，不能篡改旧清单SHA来“对上”。

## 片尾逐帧与画面异常

完整解码、正确帧数和音轨都不能排除可正常解码的黑帧、重复冻结或场景突变。合同要求逐帧检查片尾最后一秒时，必须从**最终MP4**实际解码并保留该区间所有显示帧。以实际视频显示结束时间取末秒，使用PTS及显示时长，包含跨越区间起点的帧并确保末帧在内；不足一秒则检查全片。记录范围依据、帧号、PTS、尺寸和文件SHA；不能用整数帧率估算后遗漏尾帧，也不以音频尾部延长视频检查区间。显示时长无法确定时记录不确定性并保守扩大覆盖，不预填完整通过。

1. 白模及对照分别检查；对照的原片栏、白模栏单独观察，避免亮的上栏掩盖黑的下栏。逐帧核对末秒内容、末帧和对应原片，确认没有无依据的黑屏、缺画面、重复冻结、模型/灯光/场景突变或额外片尾。缩略联系表用于覆盖定位，可疑帧回到交付尺寸查看，不声称缩略图等同全尺寸检查。
2. 全片的黑帧、突亮/突暗、重复帧或频闪检测可辅助找候选区间；登记检测尺寸、阈值和覆盖范围，再读该区间及相邻原片。合理暗场、原片静止和正常硬切不因简单阈值自动判错；反之，时间戳连续或检测器无报警也不是内容验收通过。
3. 采用自动检测或汇总判定时，用实际可解码的故障媒体验证：末尾短黑屏应被定位；上栏有画面但下栏黑屏不能漏报。确认故障会让对应内容检查及完整验收状态保持失败，而非只落入旁路计数。测试素材不冒充当前成片证据。
4. 记录实际人工所看帧及未覆盖范围。异常按当前适用要求处理，不以“已解码”或通用的部分交稿流程宣称满足尚未通过的正式验收条件。用户另行明确改变交付范围或要求先看候选时，记录范围变化并交付所选文件，保留真实未通过项；附件不覆盖用户当前明确指令，交付许可也不把未通过项变成验收合格。

### 内容扫描工具

使用包内 `scripts/content_audit.py`，不再临时用稀疏抽帧代替全片内容扫描。运行环境为 Python 3.10+、PyAV、NumPy、Pillow；缺依赖时按环境许可安装 `python -m pip install av numpy Pillow`，工具不自行安装依赖。

```sh
python scripts/content_audit.py --reference original.mp4 --white white.mp4 --comparison comparison.mp4 --out content-audit-new
```

三个输入须共用起点且时间轴未变，对照须等高上下两栏；有剪辑、偏移或变速时先明确映射，不能把最近PTS匹配当作重定时。输出目录须为空或不存在。工具完整解码每个输入，逐帧记录PTS、全画面及对照各栏的亮度/暗像素比例/重复亮度哈希，按相对PTS匹配原片，汇总近黑候选与未匹配帧。默认近黑候选为灰度值≤10的像素达到98%；阈值可用 `--luma-threshold`、`--dark-fraction` 调整并进入报告。

工具以相邻PTS确定非末帧的显示区间，按末帧已知显示时长确定结束时间，导出末秒所有显示帧及上下栏的解码尺寸JPEG、联系表和SHA，包含跨越末秒起点的VFR帧；文件名帧号为零基。末帧时长缺失时，从末帧PTS前一秒保守扩大导出，`duration_seconds` 为null、`tail_extraction_status` 为 `conservative_unverified`，并登记 `timing_review_items`，不把名义帧率估值当作准确片尾。

`content_report.json` 的 `content_scan_complete` 只表示执行完成；近黑候选、PTS未匹配或片尾时长不确定时为 `review_required`，`visual_acceptance` 始终是 `unverified`。退出码0不表示视觉通过，非零表示执行错误；重复亮度哈希仅作观察，不据此把正常静止判为冻结。人工查看范围另行登记；动作、穿插、非近黑遮挡、闪烁和音轨仍按原验收流程核对。

## 赶稿时冻结与导出

用户明确说“先出一版”“别补了，赶快导出”时，停止新增造型、动作、空间候选和扩大审查，通知协作者同样收束。不要一边答应导出一边继续试修；保留进行中的失败候选，完成已冻结版本所需的导出与核验即可。

- **逐片选版。** 记录将使用的新源、沿用旧源及对应媒体SHA。已可用的新修订可以纳入；仍有可见回归的新候选不因版本号更大而替代稳定旧版。沿用旧版必须明说，不能把新工程与旧成片混成同一修复结果。
- **冻结后不再改画面。** 对确实变更的片段，使用当前冻结源完整导出；未改变的片段核验现有文件与来源即可，不无故重复渲染。导出期间只处理阻止打开、编码、声音或打包的具体错误，不新增视觉优化。
- **规格保持。** 赶稿不自动授权降低分辨率、帧率、码率或删掉音画尾部。可先发明确标注尺寸的快速预览，但不能用放大的低清冒充原生4K；正式输出继续满足现有合同。
- **许可与结论分开。** 清单写“交稿版/未结反馈”，列明哪些修了、哪些沿用、哪些未修完。保留视觉报告的failed/unverified，不为了让全通过打包器放行而改状态。部分交稿应有独立、明确的选择记录和适用检查范围；不得据此削弱后续完整验收。
- **交付实际文件。** 完成所选版的解码、帧数、音轨、来源和包完整性核对，复用仍有效的检查，不追加无关实验。清单、说明和当前入口指向同一批文件；包内说明应反映已经导出的状态，不能仍让用户寻找未随包提供的候选预览。给出可点击文件，并用一句话指出关键未完成项。
